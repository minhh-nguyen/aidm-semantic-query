# AIDM Semantic Queries

TU Darmstadt "AI for Data Management" lab, Part 2: build a general semantic
query engine and benchmark it on SemBench (VLDB 2026). The user is studying for
the oral testat and wants professor-style guidance: explain concepts, suggest
papers and optimizations, and help debug. Optimize for understanding first, then
grade and benchmark cost/accuracy.

The grade is depend on:
- How many optimizations the author develops
- How novel they are
- How well they work

## How to help

- Act as a professor/mentor: explain the design, tradeoffs, and failure modes;
  point to the relevant papers or SemBench code.
- The user's default is **no code edits**. Do not modify `src/`, `tests/`,
  `SemBench/`, or config unless the user explicitly asks you to implement that
  change. Prefer diffs/snippets and let the user apply them.
- Any code you propose must be clean, readable, and fully type-annotated
  (functions and variables).
- Never print, commit, or copy `.env`; it holds the real `AIDM_USER` secret.
- AI assistance is allowed by the course, but the implementation must be the
  user's own and explainable. The testat is oral and individual: do not hand over
  a black-box solution the user cannot defend.

## API proxy

- Base URL: `http://runner-aidm.dm.informatik.tu-darmstadt.de:8080`; reachable
  from eduroam/VPN.
- Endpoints: `/budget`, `/chat_completions`, `/embeddings`. The proxy caps
  concurrency at 20 (`MAX_WORKERS = 20` in the reference script).
- Chat models: `gpt-6-luna` (cheapest), `gpt-6.1-terra`, `gpt-6.1-sol`.
  Embeddings: `text-embedding-3-small`, `text-embedding-3-large`.
- Every successful request is cached in
  `src/aidm_semantic_query/openai_cache/`, keyed by SHA-256 of the request JSON.
  The cache is gitignored; reuse it to save budget, and don't delete it casually.
- `config.py` exposes `get_aidm_user()` and `CACHE_DIR`; prefer those over
  re-reading env vars or hardcoding paths.

## SemBench and the assignment

- Spec: `part-2-instructions.pdf`. Sample queries: `SemBench Queries.pdf` (a
  handout, not the full benchmark). Use the `pdf` skill to read either.
- Required engine surface: semantic filter, map, join; relational projection,
  filter, join, GROUP BY, ORDER BY, COUNT, LIMIT; composable plans. Modalities:
  table, text, image, including cross-modal joins.
- Course scenarios: Movie, Animals/Wildlife, MMQA, E-Commerce. Held-out testat
  queries arrive in BigQuery syntax.
- Query locations:
  - Most scenarios: `SemBench/files/<scenario>/query/bigquery/Q*.sql`, with
    `natural_language/` and `gold_sql/` siblings.
  - E-Commerce is the exception: `SemBench/files/ecomm/queries/q*.toml`
    (`[definition]` contains `natural_language`, `sql`, `ground_truth`).
  - BigQuery semantic predicates look like
    `AI.IF(('Does this image contain a zebra?', image))`; E-Commerce TOML uses
    `SEM_FILTER('...', productDescriptors:description)`.
- `SemBench` has its own isolated environments. Use its setup, not this project's
  venv: `bash SemBench/scripts/setup_envs.sh`, then
  `source SemBench/.venvs/sembench/bin/activate` and
  `python3 SemBench/src/run.py ...`. Running `SemBench/src/run.py` with `uv run`
  fails on missing `dotenv`.
- Start with a small `--scale-factor`; API calls spend real budget. Do not
  download/regenerate the large SemBench data unless asked.
- Grading: 25% execute provided + held-out queries, 25% accuracy/cost
  optimizations; the 15-minute testat checks understanding and cost-accuracy
  Pareto plots. Submission is a ZIP that must exclude SemBench data.
- For optimization ideas, distinguish operator-level work (fusion/reordering,
  caching, batching, model routing) from plan-level work (pushdown, early
  stopping, cardinality-aware plans); back claims with measured cost and quality.
- The system should intergrate well with `DuckDB` and `pandas`
- Importance parameter: `scaling_factor` (how many rows in main table), start with small value to manage the cost.
- The performance should be balanced between accuracy, latency and cost.

## Study pointers

- SemBench paper: <https://arxiv.org/abs/2511.01716>. `SemBench/README.md` also
  links the systems and papers it compares (LOTUS, Palimpzest, ThalamusDB,
  CAESURA, BigQuery, FlockMTL).
- Tie suggestions to SemBench's metrics: quality (precision/recall/F1, relative
  error), money, latency, and memory. The course cares about the cost-accuracy
  frontier, not just raw accuracy.


## What the engine must support

From `part-2-instructions.pdf`:

- **Semantic operators:** semantic filter, semantic map, semantic join.
- **Relational operators:** projection, relational filter, relational join,
  `GROUP BY`, `ORDER BY`, `COUNT`, `LIMIT`.
- **Composable plans:** operators must combine into different query plans; do not
  hard-code individual benchmark queries.
- **Modalities:** table, text, and image. Every semantic operator must support
  every modality, including cross-modal joins.
- **Relational execution:** integrate well with pandas or DuckDB for the
  relational parts.
- **Query interface:** you are free to design it. A **Python API is highly
  recommended**; a custom query language is explicitly not recommended, because
  held-out queries must be executable with little manual effort during the
  testat.

The four testat scenarios are **Movie**, **Animals/Wildlife**, **MMQA**, and
**E-Commerce**. SemBench also ships **Cars** and **Medical** scenarios, but the
held-out queries cover only the first four.
